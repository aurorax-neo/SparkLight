# 抖音 PC/Web IM 续火花全链路复刻与排查复盘指南

## 一、事故背景与现象回顾

### 1. 08:47 自动续火中断与会话失效事件
- **触发背景**：用户将每日定时续火时间调整为 08:47。定时任务触发后，账号 A（12345678）因今日已发正常跳过；账号 B（衬我孤独_）在执行向联系人（Urr_y）发送时，收到服务端回执但未通过校验，产生 `PCIM_INIT_ACK` 失败，记录状态保持 `UNKNOWN`。
- **级联失效**：随后立即触发会话后检（`SEND_POSTCHECK`），官方身份接口返回 HTTP 200、错误码 13（明确标识登录过期）。账号 B 被标记为 `EXPIRED`，导致账号其余待续火好友全部被跳过。
- **多端同步失效**：不仅 108 容器内的 Cookie 失效，用户在独立浏览器环境中的同一账号会话也同步出现官方错误码 13，证实会话是被抖音服务端主动踢下线，而非本地客户端判定错误。

### 2. 误报与任务穿透受阻现象
- **单目标测试误报**：当互测账号今日在抖音已成功发送过消息时，用户在网页端点击“测试”，前端弹出红色错误提示“火花互动测试未成功”，将正常的“防重跳过”误当成发送失败。
- **首目标失败中断全批次**：在账号 B 的联系人列表中，由于首个目标存在当日未决记录，调度器错误地设置了全局阻断标志并直接跳出循环，导致排在其后的 5 位真实好友（包括 381 天、165 天、146 天等关键火花）连带被跳过。

## 二、根因剖析：临时公钥分支 vs 官方四层链路

此前实现之所以频繁遇到服务端踢下线，根源在于依赖了“单次临时公钥初始化分支”的短路假象，与官方浏览器的完整交互协议存在结构性脱节。

```
【此前临时分支缺陷】
每条消息 ──> 随机生成 P-256 新密钥 ──> 发送 naked 初始化声明 ──> 缺少签名与 DTrait ──> 服务端判定异常 ──> 拒绝回执并注销会话

【方案 A 官方复刻链路】
账号建联 ──> 持久化专属 P-256 密钥 ──> TokenBeat 官方握手 ──> 获得服务端票据 ──> 动态 ECDSA 签名 + DTrait 风控头 ──> 消息送达且会话长久有效
```

### 1. 临时公钥分支的致命缺陷
- **无状态裸发**：每次发信现场生成一把随机 P-256 密钥，向发信接口声称自己是“首次初始化”。服务端面对同一个会话频繁上报不同的未注册公钥，且从未经过常规握手，直接触发反爬与风控规则。
- **剥离安全头与 Cookie**：此前逻辑主动清除了 Cookie 中的旧 Guard 字段，同时未挂载 `x-tt-session-dtrait`，请求在协议特征上与真实 PC 客户端完全不符。
- **用完即弃**：发信完成后直接丢弃密钥，不保存服务端响应头中下发的安全票据，导致会话无法形成正常的认证闭环。

### 2. 官方四层安全规范
官方 PC/Web 端的正常通信建立在以下四层协作体系上：
1. **身份层 (Identity)**：通过安全接口获取 10 分钟有效期的 `identity_security_token` 及 `device_id`，注入 Protobuf 报文头。
2. **密钥层 (Ticket Guard Key)**：每个浏览器会话绑定固定的 P-256 EC 密钥对。
3. **保活握手层 (TokenBeat & Server Data)**：通过官方保活接口上报公钥，获取服务端签发的 `ticket`、`ts_sign`、`client_cert`（以 `pub.<public_key>` 形式与本地公钥严格绑定），并在心跳中自动合并轮转的 `Set-Cookie`。
4. **签名风控层 (Sign & DTrait)**：每次向敏感接口发信时，使用私钥对 `ticket={ticket}&path={path}&timestamp={timestamp}` 执行动态签名生成 `client-data`，并携带 AES+RSA 加密的 `x-tt-session-dtrait` 设备特征头。

## 三、方案 A 落地架构与实现细节

### 1. Guard 密钥与材料持久化
- **代码位置**：`src/douyin/pcim_guard.rs`、`src/douyin/im_auth.rs`
- **实现机制**：
  - 在 `WebSessionContext` 中扩展字段：`guard_secret_hex`（32 字节私钥标量）、`guard_server_data`（服务端下发的票据 JSON）、`guard_acquired_at`（票据获取时间戳）、`last_beat_at`（上次心跳时间）。
  - `GuardKey` 增加 `from_hex` / `to_hex` / `from_slice` / `to_bytes`，私钥标量使用机器主密钥（XChaCha20-Poly1305）加密后存入数据库 `account_web_contexts`。
  - 在 `acquire_im_identity` 刷新 10 分钟 IM 令牌时，显式继承上一轮上下文中的 Guard 密钥与票据，避免令牌续期冲掉 Guard 状态。

### 2. 官方 TokenBeat 握手与会话保活
- **代码位置**：`src/douyin/client.rs::passport_token_beat`、`src/douyin/web.rs`
- **实现机制**：
  - 开放官方保活接口（GET 方式）白名单。
  - 首次运行或票据缺失时，带上 `key.initialization_headers()` 与声明 Cookie 请求保活接口，从响应头或 Cookie 中解出 `bd-ticket-guard-server-data`，调用 `key.bind_response_headers` 构建 `BoundGuardMaterial`。
  - 已有票据时，通过 `key.sign_path(..., mode=Ecdsa)` 生成签名头保活。
  - 响应通过 `merge_response_headers` 自动更新并保存官方下发的轮转 `Set-Cookie`，使 Cookie 处于持续活跃状态。

### 3. 全签名发信与 DTrait 风控头装配
- **代码位置**：`src/douyin/pcim_init.rs`、`src/douyin/pcim_dtrait.rs`
- **实现机制**：
  - 弃用临时公钥声明，引入 `GuardSendAuth::Signed { key, material }`。
  - 发信前调用 `ensure_guard_bound()`：若本地已有未过期票据（600 秒内）直接复用；若缺失或过期则自动执行一次 TokenBeat 握手重新取得。
  - 调用 `key.sign_send` 计算 `bd-ticket-guard-client-data`（包含动态生成的 ECDSA 签名及秒级时间戳）。
  - 通过 `acquire_dtrait_config` 拉取官方 RSA 配置，使用 `DTraitCipher` 和 `FeatureProtocol` 动态生成 820 字节的 `x-tt-session-dtrait` 请求头。
  - 挂载完整的原生有效 Cookie，不再粗暴剥离安全字段。
  - 发信成功后，若服务端在响应中下发了轮换票据，立即写回数据库。

## 四、调度器与交互误报修复

### 1. 修复单目标占用阻断整账号的缺陷
- **修改前**：发信结果返回错误时无条件设置 `client.send_blocked = true`，导致排在前面的目标若因当日已发或已占用跳过时，整账号其余好友被强制取消。
- **修改后**：在 `pcim_init.rs` 中明确区分错误阶段：仅在真正与平台通信失败或协议异常时才阻断发送；若仅为 `DAY_CLAIM`，绝不阻断客户端全局状态。在调度批处理循环中增加预检，遇到当日已有记录的目标直接 `continue` 处理下一位好友。

### 2. 修复单目标测试成功误报为失败的问题
- **修改前**：单目标测试遇到“今日已发送”时返回 `success: false`，导致前端 Toast 弹出红色的“测试未成功”。
- **修改后**：在路由处理层识别“今日已发送/已确认送达”语义，映射为正常的成功响应：“今日火花已在抖音点亮，无需重复续火”，前端以绿色成功状态呈现。

### 3. 手动单目标强制测试通道
- 在单目标测试模式下允许传入 `force=true`，当用户在控制台手动点击测试时，即便今日早些时候有过历史记录，也能执行真实的发送验收。

## 五、参数来源与动态性审计矩阵

以下参数经全面排查，**无任何静态写死或网页抓取硬编码**：

| 参数项 | 代码生成来源 | 动态变化依据 |
|---|---|---|
| P-256 密钥对 | `pcim_guard.rs::GuardKey::generate` | 账号初始化时由操作系统随机数发生器生成 |
| Guard 签名 (`req_sign`) | `pcim_guard.rs::sign_path` | 每次发信时间戳不同，且 ECDSA 采用随机 k-nonce，签名逐次不同 |
| DTrait AES 密钥 | `pcim_dtrait.rs::DTraitCipher::new` | 每次调用由 `OsRng` 生成全新 16 字节密钥，RSA 加密后传输 |
| DTrait IV | `pcim_dtrait.rs::central_header` | 每次发信由 `OsRng` 生成全新 16 字节随机 IV，密文逐次不同 |
| Client Message ID | `pcim_init.rs:277` | 每次发信通过 `uuid::Uuid::new_v4()` 生成全局唯一标识 |
| 身份 Token 与设备 ID | `client.rs:235` | 运行时请求官方接口实时获取，服务端动态颁发 |

## 七、会话失效排查实录与平台反爬机制深度分析

在后续运维与实操中（例如用户添加新目标“邻居家的坏孩子”后发送再次触发 Cookie 判定失效），团队进行了全链路网络报文与内存状态排查，发现了以下关键机制：

1. **蜜罐探测接口陷阱 (`/passport/token/beat/web/`)**：
   - 抖音官方对该接口施加了极严格的浏览器前端 WAF 指纹防护；
   - 服务端后台如果直接向该接口发起无头 HTTP 请求，平台会直接返回 HTTP 403 Forbidden；
   - 底层收到 403 后触发 `stop_requests(Verify)`，不仅将该会话内存封禁 24 小时，还会污染调度器导致账号被误打成 `EXPIRED`；
   - **处置**：彻底移除所有对 `/passport/token/beat/web/` 的 HTTP 调用与路由登记，以轻量原生的 `passport/account/info/v2` 作为会话探测接口。

2. **发信接口 (`/v1/message/send`) 属于 Consumer 路径**：
   - 官方 JS 逆向证实该接口只消费签名，不支持裸公钥注册（Initial 声明）；
   - 严禁携带临时生成的 P-256 公钥向此接口裸发；
   - 必须通过已绑定的 `GuardKey` 和 `sign_send` ECDSA 签名出网。

3. **内存阻断死锁与探针解绑**：
   - 当会话遭遇网络波动或单接口错误时，不能把账号的会话哈希盲目封死 24 小时；
   - 在 `check_cookie()` 和用户主动点击“检测有效性”时，允许发起真实 Passport 探针，若服务端返回 200 有效则立即清除内存阻断，避免死锁。
